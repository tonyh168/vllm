# 第 10 章 动手实验：7 个 15 分钟的小实验

> 目标：每个实验都是"改一个地方 → 观察行为变化"。**读十遍源码不如自己看到数字变一次。**
> 每个实验都给了"预测"和"观察点"，先预测再看结果 —— 预测错了才是学到东西的地方。

准备一个终端跑服务，另一个跑压测：

```bash
# 终端 1
VLLM_LOGGING_LEVEL=INFO .venv/bin/vllm serve Qwen/Qwen3-0.6B --max-model-len 4096

# 终端 2（压测）
.venv/bin/vllm bench serve --model Qwen/Qwen3-0.6B \
  --dataset-name random --random-input-len 512 --random-output-len 128 \
  --num-prompts 200 --request-rate 20
```

---

## 实验 1：看见"批"的存在

**做法**：在 `vllm/v1/core/sched/scheduler.py` 的 `schedule()` 开头加一行：

```python
logger.info("step: running=%d waiting=%d budget=%d",
            len(self.running), len(self.waiting), token_budget)
```

**预测**：并发压测下，`running` 会快速上升然后稳定；`waiting` 在 0 附近。

**观察点**：
- `budget` 每步都被扣减，扣到 0 就停 —— 这就是 `max_num_batched_tokens` 的实际作用。
- 当你把 `--max-num-seqs` 调小，`waiting` 开始 > 0。

**升级**：把日志去掉，改用 `--max-num-seqs 1` 和 `--max-num-seqs 256` 各压一次，比较吞吐。**这就是 batch 大小对吞吐的影响曲线。**

---

## 实验 2：`max_num_batched_tokens` 是 prefill/decode 的旋钮

**做法**：分别用三组参数压测，记录 TTFT 和 TPOT：

```bash
# A：小预算
vllm serve ... --max-num-batched-tokens 2048
# B：默认
vllm serve ...
# C：大预算
vllm serve ... --max-num-batched-tokens 32768
```

**预测**：预算越大，TTFT 越低（长 prompt 一次算完），但 TPOT 越高（decode 请求陪跑大 prefill）。

**观察点**：`vllm bench serve` 输出里的 `Mean TTFT` 和 `Mean TPOT`。你应该看到两者朝相反方向移动。

**为什么**：这正好对应第 3 章的 `token_budget` 分配 —— prefill 吃掉的预算就是 decode 被拖慢的原因。

---

## 实验 3：抢占是显存不足的信号

**做法**：用小显存模拟压力：

```bash
vllm serve Qwen/Qwen3-0.6B --max-model-len 4096 \
  --gpu-memory-utilization 0.30 --max-num-seqs 256
```

然后用长 prompt、高并发压测。

**预测**：日志里出现 `Waiting` 上升，`preempted` 计数 > 0，吞吐明显下降。

**观察点**：
- `SchedulerStats.num_preempted_reqs`（日志行里或 `/metrics`）。
- **`num_preempted_reqs > 0` 意味着有请求的 prefill 被白算了一遍。**
- 打开 prefix caching 后再压一次，看抢占的代价是否降低（被抢占的请求重算时能命中缓存）。

**为什么**：对应第 3 章 `_preempt_request` —— 抢占 = 释放全部 block + `num_computed_tokens = 0`。

## 实验 4：prefix caching 的威力与陷阱

**做法 A（威力）**：写一个共享 3000 token system prompt 的脚本，发 100 个请求，只改最后一句。

```bash
# 观察日志里的 Prefix cache hit rate
```

**预测**：第一次请求之后，`Prefix cache hit rate` 接近 90%+，TTFT 骤降（因为 3000 token 的 prefill 被跳过了）。

**做法 B（陷阱）**：用同样的 3000 token prompt 压测，但**对比开/关 prefix caching 两种配置**。

**预测**：开着的时候吞吐数字好看得多 —— 但这不是"计算快"，而是"计算被跳过了"。**如果你用固定 prompt 做容量规划，会严重高估系统的真实能力。**

**观察点**：`gpu_model_runner` 里打一行 `num_computed_tokens` 的日志，你会看到第二次请求的 prefill 长度几乎为 0。

## 实验 5：CUDA Graph 到底省了什么

**做法**：

```bash
# A：eager
vllm serve ... --enforce-eager
# B：piecewise
vllm serve ... -O1
# C：full+piecewise（默认）
vllm serve ... -O2
```

用固定的短输入短输出压测（例如 `--random-input-len 32 --random-output-len 64`），**重点看小并发下的延迟**。

**预测**：并发越小，CUDA Graph 的收益越明显（因为 CPU launch 开销占比越大）。高并发时差距缩小。

**观察点**：日志里的 `Capturing CUDA graphs` 段会打印捕获了哪些 size。把 `--compilation-config '{"cudagraph_capture_sizes": [...]}'` 改一下，观察捕获数量与启动时间的关系。

**为什么**：CUDA Graph 消除的是**每个 kernel 的 launch 开销（CPU 侧）**，所以 batch 越小、kernel 越快，占比越高。

## 实验 6：看见 `slot_mapping` 和 handoff

**做法**：在 `vllm/v1/worker/block_table.py` 的 `compute_slot_mapping`（第 201 行）后面加：

```python
if num_reqs == 1:
    print("slot_mapping[:16] =", self.slot_mapping.gpu[:16].tolist())
```

发一个短请求（prompt 长 40 个 token，block_size=16）。

**预测**：你会看到类似 `[0, 1, 2, ..., 15, 16, 17, ...]` 的序列（第一个块占满后进入第二个块）。

**升级实验**：让两个请求并发，观察它们的 `slot_mapping` 是否交错（不同的物理块）。然后手动 `reset_prefix_cache` 再跑，看块号分配是否变化。

**为什么**：这是第 5 章那个公式的实证：`block_id * block_size + offset`。

## 实验 7：推理请求在模型里走一遍

**做法**：在模型 forward 的最外层打点。以 Llama 类模型为例，找 `vllm/model_executor/models/llama.py` 的 `LlamaModel.forward`，加：

```python
print("forward called, positions[:8] =", positions[:8].tolist(),
      "input_ids[:8] =", input_ids[:8].tolist())
```

**预测**：
- **prefill**：一次调用，`positions` 是 `[0,1,2,...,n-1]`，`input_ids` 是 prompt。
- **decode**：一次调用，`positions` 是 `[n]`，`input_ids` 是上一步生成的 token。

**观察点（关键）**：如果两个请求在同一个 batch 里，你会看到 **一次** forward 调用里 `positions` 是 `[0,1,2,...] + [n, ...]` —— **两个请求的 token 被拼在一个张量里**。这就是连续批处理。

**为什么**：对应第 5 章的 `_prepare_inputs`：所有请求的 token 被 flatten 成一个 `[total_tokens]` 张量，用 `query_start_loc` 标记边界。

## 附：3 个更长的进阶实验（有 GPU 时间再做）

### 实验 8：量化对 decode 的影响

同一个模型，对比 FP16 与 FP8（或 AWQ）：
- 权重显存减半 → KV block 数增加 → 并发上限提高。
- decode 每步要读的权重量减半 → **memory-bound 的 decode 直接加速**。

记录：`GPU KV cache size: N tokens` 的变化 + 吞吐变化。

### 实验 9：投机解码的接受率曲线

开投机解码（如 MTP 或 n-gram），在 `/metrics` 里找 `accepted_tokens_per_pos`：
- 第 1 个草稿位置接受率通常最高，往后递减。
- **如果第 1 位就低于 40%，说明这个 workload 不适合投机解码**（草稿质量差）；把 `-num_speculative_tokens` 调小。

### 实验 10：TP 的代价

同一模型用 `-tp 1` 和 `-tp 2`（或 4）各压一次：
- 只看吞吐：TP 可能略有提升（算力上去了）或持平。
- **看 TPOT**：TP 的每层两次 all-reduce 会让单步延迟变差。
- 观察启动日志里选中的 all-reduce 实现（custom / quick / NCCL）。

**结论**：如果模型放得下单卡，`-dp` 通常比 `-tp` 更划算。
