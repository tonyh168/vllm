# 第 0 章 先跑起来：让日志出现在屏幕上

> 目标：30 分钟内跑通一次离线推理和一次在线服务，并学会"看日志判断 vLLM 在干什么"。
> 这一章不要求你理解任何内部结构，只需要你**有观察素材**。

## 0.1 环境准备

本仓库用 `uv` 管理 Python 环境（见仓库根目录 `AGENTS.md`）。**不要用系统 `python3` 或裸 `pip`**。

```bash
# 安装 uv（如果还没有）
curl -LsSf https://astral.sh/uv/install.sh | sh

uv venv --python 3.12
source .venv/bin/activate

# 用预编译产物做 editable 安装，避免从源码编译 CUDA 算子（省下 1 小时）
VLLM_USE_PRECOMPILED=1 uv pip install -e . --torch-backend=auto
```

验证安装：

```bash
.venv/bin/python -c "import vllm; print(vllm.__version__)"
```

## 0.2 实验 A：离线推理（Offline Inference）

`vllm/entrypoints/llm.py` 里的 `LLM` 类是最简单的入口。仓库自带示例 [`examples/basic/offline_inference/basic.py`](../examples/basic/offline_inference/basic.py)：

```python
from vllm import LLM, SamplingParams

prompts = ["Hello, my name is", "The capital of France is"]
sampling_params = SamplingParams(temperature=0.8, top_p=0.95)

llm = LLM(model="facebook/opt-125m")     # ① 初始化：加载权重、配 KV cache、编译/热身
outputs = llm.generate(prompts, sampling_params)  # ② 推理
for o in outputs:
    print(o.prompt, "->", o.outputs[0].text)
```

跑起来：

```bash
# 打开详细日志，方便看清初始化每个阶段
VLLM_LOGGING_LEVEL=DEBUG .venv/bin/python examples/basic/offline_inference/basic.py
```

### 你会看到的日志，以及它在说什么

初始化阶段（`LLM.__init__`）依次做这些事，日志里能一一对应：

| 日志关键词 | 实际发生的事 | 源码位置 |
| --- | --- | --- |
| `Loading model weights` | 从 safetensors 读权重并按 TP/量化切分 | `vllm/model_executor/model_loader/loader.py` |
| `Starting a local engine` / `EngineCore` | 启动引擎核心（多进程或同进程） | `vllm/v1/engine/utils.py`（`launch_core_engines`） |
| `Memory profiling` | 跑一次假前向来测峰值显存 | `vllm/v1/worker/gpu_worker.py:510` `determine_available_memory` |
| `GPU KV cache size: N tokens` | 用剩余显存除以每 token 的 KV 字节数，得到能缓存多少 token | 同上 + `get_kv_cache_spec` |
| `Available KV cache memory: X GiB` | 扣掉权重、激活、CUDA Graph 之后的可用空间 | 同上 |
| `Capturing CUDA graphs` / `torch.compile` | 编译计算图并录制 CUDA Graph | `vllm/v1/worker/gpu_worker.py:747` `compile_or_warm_up_model` |
| `init engine` | 全部就绪，进入 busy loop | `vllm/v1/engine/core.py:1411` `run_busy_loop` |

推理阶段（`llm.generate`）你会看到一行行统计日志（默认每几秒一条），形如：

```text
Engine 000: Avg prompt throughput: 12.3 tokens/s, Avg generation throughput: 456.7 tokens/s,
Running: 4 reqs, Waiting: 0 reqs, GPU KV cache usage: 3.1%, Prefix cache hit rate: 0.0%
```

这行日志是**整个教程最重要的观测量**，逐字段解释：

- `Avg prompt throughput`：这一区间内 prefill 处理的 prompt token 速率。
- `Avg generation throughput`：decode 产出 token 的速率 —— **这是吞吐的主要指标**。
- `Running / Waiting reqs`：正在跑的请求数（= batch 大小）/ 在等 KV 空间的请求数。**`Waiting > 0` 说明 KV 显存不够，正在排队**。
- `GPU KV cache usage`：KV 显存利用率。**长期接近 100% 是健康的**（说明显存没浪费），但 `Waiting` 同时很大就说明该扩显存/降并发。
- `Prefix cache hit rate`：前缀缓存命中率，> 0 说明有 prompt 复用。

> 💡 **性能视角**：这五个数字就是 vLLM 调优的仪表盘。
> `Waiting` 涨 → 显存瓶颈；`generation throughput` 低但 `KV usage` 也低 → batch 太小（`max_num_seqs` 或请求量不够）；
> 吞吐高但 TTFT 高 → chunked prefill 参数需要调。

## 0.3 实验 B：在线服务（Online Serving）

```bash
VLLM_LOGGING_LEVEL=INFO .venv/bin/vllm serve Qwen/Qwen3-0.6B --max-model-len 4096
```

另开一个终端请求：

```bash
curl http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen3-0.6B","prompt":"The capital of France is","max_tokens":32}'
```

然后看日志：请求进来时，你会看到 `Running` 从 0 跳到 1；如果你并发发 20 个请求，会看到 `Running` 上升、`GPU KV cache usage` 上升，直到出现 `Waiting`。

### 在线服务比离线多了什么

| 进程 | 职责 | 代码 |
| --- | --- | --- |
| API Server | 收 HTTP、tokenize、流式回包 | `vllm/entrypoints/launchers/api_server`、`vllm/entrypoints/openai/` |
| Engine Core | 调度 + KV 管理 + 驱动 worker | `vllm/v1/engine/core.py` |
| GPU Worker ×N | 真正跑模型 | `vllm/v1/worker/gpu_worker.py` |

离线 `LLM` 默认把 Engine Core 放在**同一个进程**里（`InprocClient`），在线服务则用**独立进程 + ZMQ** 通信（`MPClient`/`AsyncMPClient`）。这个区别会在第 1 章展开。

## 0.4 学会用 `nvidia-smi` 和日志验证你的判断

```bash
# 另开一个终端，1 秒刷新一次显存
watch -n 1 nvidia-smi --query-gpu=memory.used --format=csv

# 或者用 vLLM 自带的环境收集脚本（提 issue 时也要用）
.venv/bin/python -m vllm.collect_env
```

观察重点：初始化结束时显存会出现一个**台阶式跳变**（KV cache 一次性预分配），此后推理过程中显存基本是平的 —— 因为 vLLM 使用**预分配 + 分页管理**，不做动态 `cudaMalloc`。这是它比朴素 PyTorch 服务稳定的关键原因之一。

## 0.5 本章小结

- 你已经有了两个可运行的入口：`LLM.generate`（离线）和 `vllm serve`（在线）。
- 你已经认识了调优仪表盘：`Running/Waiting/GPU KV cache usage/throughput/prefix hit rate`。
- 你知道了初始化阶段的大致顺序：加载权重 → 测显存 → 分配 KV cache → 编译/录制 CUDA Graph。

⚠️ **易错点**
- `.venv/bin/python` 与 `python3` 混用会导致 `ModuleNotFoundError: vllm._C`。始终用 `.venv/bin/python`。
- 首次运行会编译 kernel 并录制 CUDA Graph，**启动慢是正常的**（几十秒到几分钟）。想跳过用 `-O0` 或 `--enforce-eager`。
- `VLLM_LOGGING_LEVEL=DEBUG` 会打印大量日志，测性能时务必关掉。
