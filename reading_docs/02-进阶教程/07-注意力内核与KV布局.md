# 第 7 章 注意力内核与 KV 布局

> **本章回答**：KV 是怎么写进分页缓存的？为什么 decode 要"两阶段"？cascade attention 省了什么？`unified_attention` 统一了什么？MLA 为什么要 prefill/decode 分开选后端？
> 涉及文件：`vllm/v1/attention/ops/`、`vllm/v1/attention/backends/`、`vllm/model_executor/layers/attention/attention.py`

## 7.1 为什么 attention 是性能工程的主战场

两种阶段的瓶颈完全不同：

| 阶段 | 算术强度 | 瓶颈 | 关键指标 |
| --- | --- | --- | --- |
| **Prefill** | 高（O(n²) 计算 / O(n) 数据） | **算力** | FLOPS 利用率 |
| **Decode** | 极低（O(n) 计算 / O(n) 数据） | **显存带宽** | 有效带宽占比 |

Decode 的算术强度 ≈ 1 FLOP/Byte 量级，远低于现代 GPU 的 100+ FLOP/Byte。**算力几乎完全闲置，全部时间在等显存。**

于是优化方向就很清楚：

1. **减少要读的数据量**：量化 KV（fp8）、MLA（压缩 latent）、sliding window（少读）。
2. **提高并行度**：split-KV（一个请求的 KV 切成多段并行算）。
3. **避免重复读**：cascade attention（公共前缀只读一次）、GQA 分组（多个 query head 共享 KV head）。
4. **让读更高效**：合适的布局（`[block, block_size, head, dim]` 而不是 `[block, head, dim, block_size]`）。

## 7.2 `reshape_and_cache`：KV 写入的唯一入口

`vllm/v1/attention/ops/triton_reshape_and_cache_flash.py:34`。

### 签名与语义

```python
key_ptr    # [num_tokens, num_heads, head_size]
value_ptr  # [num_tokens, num_heads, head_size]
key_cache_ptr    # [num_blocks, block_size, num_heads, head_size]
value_cache_ptr  # [num_blocks, block_size, num_heads, head_size]
slot_mapping_ptr # [num_tokens]
```

**注意输入和缓存的布局差异**：输入是"每 token 连续"，缓存是"每 block 连续"。`reshape_and_cache` 就是这个转置（reshape）操作。

### 核心逻辑

```python
token_idx = tl.program_id(axis=0)                      # 一个 program 处理一个 token
slot_idx = tl.load(slot_mapping_ptr + token_idx).to(tl.int64)
if slot_idx < 0:
    # Padding token that should be ignored.
    return                                             # ★ 负数 slot = 不写
block_idx = slot_idx // block_size
block_offset = slot_idx % block_size
```

**这就是第 5 章 `ComputeSlotMappingKernel` 的逆运算**：
- `ComputeSlotMappingKernel`：给 (req, position) → 算出 slot；
- `reshape_and_cache`：给 slot → 算出 (block_idx, block_offset) → 写入。

### 两种布局

```python
use_head_major_layout = key_cache.ndim == 5
```

| 布局 | 形状 | 适用 |
| --- | --- | --- |
| 标准（`ndim == 4`） | `[num_blocks, block_size, num_heads, head_size]` | 大多数后端 |
| head-major（`ndim == 5`） | `[num_blocks, num_heads, head_size/x, block_size, x]` | 兼容旧的自研 paged attention kernel |

**为什么要有"head-major + x 分解"？** 这是 `docs/design/paged_attention.md` 里讲的优化：把 `head_size` 拆成 `x` 段（`x` = 16 字节 / element_size），使**相邻线程读相邻内存**（内存合并 coalescing）。

```cpp
const scalar_t* k_cache,   // [num_blocks, num_kv_heads, head_size/x, block_size, x]
const scalar_t* v_cache,   // [num_blocks, num_kv_heads, head_size, block_size]
```

注意 K 和 V 的布局**不一样**：V 是 `[head_size, block_size]` —— 即**转置存储**。因为 V 的访问模式是"同一个 head 维度跨多个 token 求点积"，转置后同一列（列 = token）连续，又利于合并。

### FP8 KV cache

```python
k_scale, v_scale,  # float32
FP8_KV_CACHE: tl.constexpr,
```

写入时可以顺便量化（乘以 scale 再存成 fp8）。`triton_reshape_and_cache_flash_per_token_head_quant`（`:272`）支持 per-token-head 的量化粒度。

⚠️ **设备要求**：FP8 KV cache 需要 SM89+（原生 fp8e4nv）。代码里有显式断言，失败时提示改用 bfloat16。

> 💡 **性能视角**：FP8 KV 的收益是**双向**的：
> - 写入量减半（`reshape_and_cache` 的带宽开销减半）；
> - 读取量减半（attention 的带宽开销减半）。
> decode 是带宽瓶颈，所以后者是主要收益 —— **KV fp8 常常能带来接近 2× 的 decode 加速**（实际因反量化开销而略低）。
> 但也引入了下游的所有 kernel 都要支持 fp8 读取的复杂度。

## 7.3 Split-KV decode：为什么需要两阶段

`vllm/v1/attention/ops/triton_decode_attention.py`。

### 问题

decode 时 batch 里每个请求只有 1 个 query，但要对着几万个 KV。**并行度严重不足** —— 一个请求只能填满少量 SM。

### 解法

```text
stage 1: 把每个请求的 KV 序列切成 S 段，每段一个 program → 输出 (partial_acc, lse)
         （并行度 = batch × S）
stage 2: 对每个请求合并 S 个 (acc, lse) → 最终输出
         （_fwd_kernel_stage2, :576）
```

### 合并的数学

softmax 满足**结合律**。给定两组"部分注意力结果" `(o₁, lse₁)` 和 `(o₂, lse₂)`，其中 `lse = log(sum(exp(scores)))`：

```text
lse_merged = log(exp(lse₁) + exp(lse₂))
o_merged   = o₁ · exp(lse₁ - lse_merged) + o₂ · exp(lse₂ - lse_merged)
```

`merge_attn_states.py:9` 的 `_merge_attn_states_torch` 就是这个公式的 PyTorch 参考实现：

```python
max_lse = torch.maximum(prefix_lse, suffix_lse)
prefix_se = torch.exp(prefix_lse - max_lse)
suffix_se = torch.exp(suffix_lse - max_lse)
out_se = prefix_se + suffix_se
prefix_scale = (prefix_se / out_se).transpose(0, 1).unsqueeze(-1)
suffix_scale = (suffix_se / out_se).transpose(0, 1).unsqueeze(-1)
merged = prefix_output * prefix_scale + suffix_output * suffix_scale
merged_lse = torch.log(out_se) + max_lse
```

用 `max_lse` 做数值稳定（和 softmax 的 `-max` 技巧同理）。`both_empty` 的处理（`masked_fill_(..., 0.0)`）对应"两段都是空"（`lse = -inf`）的情况 —— 这在 chunked prefill 和 sliding window 下会真实发生。

### "grouped" 版本

`_fwd_grouped_kernel_stage1`（`:279`）/ `_decode_grouped_att_m_fwd`（`:470`）：

**GQA/MQA 下多个 query head 共享一个 KV head** —— 让一组 query head 的 program 共同加载一次 KV，把 KV 读取量摊薄。这是 GQA 模型（如 Llama 3）的必需优化。

## 7.4 `unified_attention`：一个 kernel 服务两种阶段

`vllm/v1/attention/ops/triton_unified_attention.py`。

混合 batch（chunked prefill + decode 同一步）的传统做法是：跑 prefill kernel + decode kernel + `merge`。三次 launch + 中间结果的显存往返。

`unified_attention`（`:802`）的做法：**一个 kernel 内部按请求类型走不同分支，用 segmentation + `reduce_segments`（`:685`）代替独立的第二阶段**。

好处：
- 一次 launch 覆盖混合 batch；
- 不需要中间张量落显存。

`_td` 后缀的辅助函数（`_load_q_td`、`_load_kv_tile_td`、`_store_output_td`）用的是 **TensorDescriptor / TMA 风格的加载**（Hopper+ 的硬件特性），进一步减少地址计算开销。

## 7.5 Cascade attention：公共前缀只读一次

`vllm/v1/attention/ops/prefix_prefill.py`。

### 问题

一批请求共享同一段长 system prompt 时，朴素实现是**每个请求都把这段前缀的 KV 从显存读一遍**。batch=32、前缀=4000 token 时，读的是 32 倍的数据。

### 解法

```text
1. 对公共前缀只做一次 attention → (prefix_acc, prefix_lse)
2. 每个请求对自己的后缀做 attention → (suffix_acc_i, suffix_lse_i)
3. 用 merge_attn_states 合并
```

实现：`context_attention_fwd`（`prefix_prefill.py:777`）。

调度侧要提供公共前缀的长度：`SchedulerOutput.num_common_prefix_blocks`。
Worker 侧计算：`_compute_cascade_attn_prefix_lens`（`gpu_model_runner.py:2656`）、`_compute_cascade_attn_prefix_len`（`:2694`）。
后端侧决定要不要用：`AttentionMetadataBuilder.use_cascade_attention`（`backend.py:734`）。

### `BASE_BLOCK` 的架构特化

```python
BASE_BLOCK = 128 on SM80+ / 64 otherwise
NUM_WARPS  = 4 on ROCm / 8 elsewhere
```

**编译期按架构选参数**，避免运行时分支。这是 kernel 工程的常规做法。

### 三个限制

1. **不兼容 CUDA Graph** —— 使用 cascade attention 的 batch 被强制分派到 `PIECEWISE`（或 `NONE`）。
2. **不兼容 ubatching（DBO）** —— `gpu_model_runner.py:4336` 有显式判断。
3. **默认关闭**（`ModelConfig.disable_cascade_attn` 默认为 `True`）。需要显式开启。

> 💡 **性能视角**：cascade attention 的收益高度依赖**前缀共享程度**。
> - 所有请求共享 90% 前缀 → 收益巨大；
> - 每个请求 prompt 都不同 → 纯粹是额外开销（多了一次 merge）。
> vLLM 因此默认关闭它，让用户在明确知道自己的 workload 时才开。

## 7.6 MLA：为什么 prefill 和 decode 要用不同后端

MLA（Multi-head Latent Attention，DeepSeek 系）把 KV 压缩成一个低维 latent，显著减少 KV 显存。但它的计算形态在两个阶段差异很大：

| 阶段 | 形态 | 合适的 kernel |
| --- | --- | --- |
| **Prefill** | 常规的 attention 形状（多个 query），可以被"展开"成标准 MHA 形式 | FlashAttention / FlashInfer |
| **Decode** | 单 query，且可以把投影矩阵**吸收**进 Q 和输出投影（absorbed MQA），避免显式展开 KV | FlashMLA / FlashInferMLA / CUTLASS MLA |

这体现在接口上：`MLAAttentionImpl`（`backend.py:983`）有两个 forward：

```python
def forward_mha(self, ...): ...   # :1014  prefill 路径
def forward_mqa(self, ...): ...   # :1029  decode 路径（absorbed）
def do_kv_cache_update(self, ...): ...  # :1052
```

以及选择器上的两个旋钮：

```bash
# decode 后端
vllm serve <model> --attention-backend FLASHMLA
# prefill 后端
vllm serve <model> -ac.mla_prefill_backend FLASH_ATTN
```

### MLA 后端一览（`vllm/v1/attention/backends/mla/`）

| 类型 | 文件 |
| --- | --- |
| 稠密 MLA | `flashmla.py`、`flashattn_mla.py`、`flashinfer_mla.py`、`triton_mla.py`、`cutlass_mla.py`、`aiter_triton_mla.py`、`rocm_aiter_mla.py`、`tokenspeed_mla.py` |
| 稀疏 MLA（DSA 风格 top-k 块选择） | `flashmla_sparse.py`、`flashattn_mla_sparse.py`、`flashinfer_mla_sparse.py`、`flashinfer_mla_sparse_sm120.py`、`rocm_aiter_mla_sparse.py`、`xpu_mla_sparse.py` |
| CPU | `amx_mla.py`（Sapphire Rapids 的 AMX）、`cpu_mla.py` |
| 稀疏 pipeline 组件 | `indexer.py`、`compressor_utils.py`、`sparse_swa.py`、`sparse_utils.py` |
| prefill 子包 | `prefill/` |

**稀疏 MLA** 是一个重要方向：一个"lightning indexer"给 KV 块打分，只对 top-k 块做 attention。KV 显存占用不变，但**读的量级下降** —— 对超长上下文（128K+）是唯一的实用手段。

> 💡 **性能视角**：MLA 的稀疏化是"用少量精度损失换数量级的带宽节省"。
> 代价是额外的 indexer 计算和侧缓存（index keys 存在单独的 cache 里），以及调参复杂度（top-k 选多少）。

## 7.8 `Attention` 层：为什么用 custom op

`vllm/model_executor/layers/attention/attention.py:218`。

```python
def forward(self, query, key, value, kv_cache, attn_metadata, output=None):
    # 可选的 query 量化（用简单 torch op，让 compile 能融进前序算子）
    # output = torch.empty(...)
    # reshape 放在 custom op 外面（在非 cudagraph 区域最小化 CPU 开销）
    if not self.impl.forward_includes_kv_cache_update:
        self.unified_kv_cache_update(key, value, layer_name)      # :539
    self.unified_attention_with_output(query, key, value, output, layer_name, ...)  # :544
```

三个设计点：

**① KV cache 更新和 attention 是分开的两个 custom op**

```python
unified_kv_cache_update(...)
unified_attention_with_output(...)
```

- 它们都是 `torch.ops.vllm.*` 注册的 custom op，这样 **Dynamo 能看见它们**（作为"不透明节点"），从而正确地在它们处切图（`splitting_ops` 就是按这些名字切的）；
- 分开的原因：有些后端把 KV 更新融合进 forward（`forward_includes_kv_cache_update`），此时只调 attention 那个。

**② reshape 放在 custom op 外面**

```python
# 注释：在非 cudagraph 区域最小化 CPU 开销
```

因为 reshape 是免费的（只是改 view），放哪里都行；但放在 custom op 外面，在 compile 时就能被**融合或消除**，而 custom op 内部对编译器是不透明的。

**③ query 量化用简单 torch op**

```python
# 注释：用简单 torch op 量化可让 torch.compile 融进前序算子，
# 避免 decode 期走 custom op 的额外开销
```

**这是个很微妙的取舍**：调用一个现成的量化 kernel 看起来更专业，但在 decode 这种小张量场景下，**让编译器把它融进前一个 kernel** 比单独 launch 一个 kernel 更快。

## 7.10 本章小结

| 技术 | 解决的问题 | 收益来源 | 代价 |
| --- | --- | --- | --- |
| KV 布局 `[block, slot, head, dim]` | 内存合并 | 带宽效率 | 写入时的转置 |
| head-major + `x` 分解 | 相邻线程读相邻内存 | 合并 | 实现复杂 |
| FP8 KV | 读写量减半 | **decode 带宽** | 需要 SM89+，反量化开销 |
| Split-KV | decode 并行度不足 | 占用更多 SM | 两阶段 + merge |
| GQA grouped decode | 多 query 共享 KV head | KV 读取摊薄 | — |
| `unified_attention` | 混合 batch 要两次 launch | 一次 launch | kernel 更复杂 |
| Cascade attention | 公共前缀重复读 | 前缀只读一次 | **不兼容 CUDA Graph**，默认关闭 |
| MLA absorbed decode | KV 太大 | 显存 + 带宽双降 | prefill/decode 要分开选后端 |
| 稀疏 MLA | 超长上下文 | 读的量级下降 | indexer 开销 + 调参 |
| custom op 包 attention | 让编译器可见 | 可切图/可捕获 | 不透明节点 |

⚠️ **易错点**
- `--block-size` 可能排除掉更高优先级的后端（vLLM 会 warning）。
- Cascade attention 默认关闭，且与 CUDA Graph / DBO 冲突。
- `reshape_and_cache` 遇到负 `slot_mapping` 会跳过 —— 这是 padding 行的处理方式，不要"修复"成写 0。
