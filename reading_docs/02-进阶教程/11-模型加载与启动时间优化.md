# 第 11 章 模型加载与启动时间优化

> **本章回答**：启动的几分钟花在哪？权重加载怎么加速？为什么 `determine_available_memory` 要真的跑一次前向？sleep mode 和 workspace 是什么？
> 涉及文件：`vllm/model_executor/model_loader/`、`vllm/v1/worker/gpu_worker.py`、`vllm/model_executor/models/registry.py`、`vllm/config/{load,offload}.py`

## 11.1 启动时间的构成

以 `-O2`（默认）为例，一个 7B 模型的启动大致是：

| 阶段 | 典型耗时 | 可否优化 |
| --- | --- | --- |
| 进程启动 + import | 5~20 s | ✅ 懒加载、预编译 |
| 权重加载（磁盘 → 显存） | 10~120 s | ✅ **预取 / 并行加载 / 更快的格式** |
| 显存 profiling（跑假前向） | 2~10 s | ⚠️ 可用 `kv_cache_memory_bytes` 跳过 |
| KV cache 分配 | 1~5 s | ❌ 必须 |
| torch.compile（Inductor） | **30~300 s** | ✅ **AOT + 缓存** |
| CUDA Graph 捕获 | **10~120 s** | ✅ 减少 capture sizes |
| Sampler / kernel warmup | 5~30 s | ⚠️ |

**结论：编译和图捕获通常是启动时间的大头**，而它们都是**可以缓存/预编译**的。

```bash
vllm bench startup --model <model>      # 分解启动各阶段耗时
```

## 11.2 权重加载：从磁盘到显存的五个加速手段

### 基类流程

`vllm/model_executor/model_loader/base_loader.py:43` `BaseModelLoader.load_model`：

```python
with set_default_torch_dtype(model_config.dtype):        # :53
    with target_device:                                   # :54
        model = initialize_model(vllm_config)             # :55  ★ 在目标 device 上直接实例化
    log_model_inspection(model)                           # :60
    self.load_weights(model, model_config)                # :64
    # 峰值显存打点                                        # :67-73
    if _has_online_quant(model_config):
        finalize_layerwise_processing(...)                # :78-79
    process_weights_after_loading(model, model_config, target_device)   # :81
    model.eval()                                          # :83
```

**`with target_device` 的意义**（第 1 章讲过的设计原则）：**参数一出生就在 GPU 上**，避免"先在 CPU 分配全量、再拷到 GPU"的双倍峰值。

> ⚠️ **这就是为什么 vLLM 不会 OOM 在一个"理论上放得下"的模型上**：如果先加载到 CPU 再拷贝，峰值显存会是"权重 ×2"。

### 手段 ①：预取到 OS page cache

`vllm/model_executor/model_loader/weight_utils.py`：

```python
def _prefetch_checkpoint(...): ...          # :742
def _prefetch_all_checkpoints(...): ...     # :759
def _get_checkpoints_size_bytes(...): ...   # :685
def _get_available_ram_bytes(...): ...      # :692
def _get_fs_type(...): ...                  # :709
```

由 `LoadConfig.safetensors_prefetch_num_threads` 和 `safetensors_prefetch_block_size` 控制。

**`_get_available_ram_bytes` 的注释值得一读**：它包含 **cgroup memory limit**（容器里不会被 host 内存误导），否则在 k8s 里会误判"内存充足"而把 page cache 挤爆。

`_get_fs_type` 通过 `/proc/mounts` 最长前缀匹配判断是否 NFS —— **NFS 上预取的收益更大**。

**原理**：多 rank（TP/DP）在启动时都要读同一份 checkpoint。如果不预取，N 个进程各自从磁盘读一遍（或至少第一遍是冷读）。预取线程**按块顺序把文件读进 page cache**，后续各 rank 的实际加载就命中了内存。

> 💡 **性能视角**：这是"**把 N 次磁盘读变成 1 次**"的经典优化。
> 大模型（几百 GB）在冷启动时的加载时间可以从几分钟降到几十秒。
> 前提是**内存足够放下 checkpoint** —— 所以 `_get_available_ram_bytes` 的判断很重要。

### 手段 ②：更快的加载格式

| `--load-format` | 迭代器 | 特点 |
| --- | --- | --- |
| `auto`（默认） | `safetensors_weights_iterator`（`:834`） | 标准 |
| — | `multi_thread_safetensors_weights_iterator`（`:971`） | 多线程读 |
| `fastsafetensors` | `fastsafetensors_weights_iterator`（`:1038`） | **fastsafetensors 库**，GPU 直读 |
| `runai_streamer` | `runai_safetensors_weights_iterator`（`:1001`） | Run:ai Model Streamer |
| `instanttensor` | `instanttensor_weights_iterator`（`:1107`） | — |
| `npcache` | `np_cache_weights_iterator`（`:639`） | 转成 numpy 缓存 |
| `pt` / `safetensors` / `gguf` / `bitsandbytes` / `tensorizer` / `sharded_state` | 各自实现 | 见 `model_loader/` 目录 |

**fastsafetensors / runai_streamer 的价值**：它们能绕过"CPU 内存中转"（或使用更高效的 I/O 路径）。

### 手段 ③：并行加载（多 rank）

多个 worker 进程本来就并行加载自己的分片。

`ParallelConfig.max_parallel_loading_workers`：在**单进程内**用多线程并行加载。

### 手段 ④：EP 权重过滤

`ParallelConfig.enable_ep_weight_filter`：**EP 下只加载本 rank 需要的专家权重**。

对 MoE 模型（几百个专家）这是巨大的收益：不是每个 rank 都要加载全部专家。

### 手段 ⑤：权重加载期间的 allocator 调优

`Worker.load_model`（`gpu_worker.py:485`）：

```python
with self._maybe_get_memory_pool_context(tag="weights"):     # 独立的 CuMem 池
    with set_current_vllm_config(self.vllm_config):
        with self._scoped_allocator_max_split(max_split_size_mb=20):   # ★
            model_loader.load_model(...)
```

`_scoped_allocator_max_split`（`:321`）把 PyTorch allocator 的 `max_split_size_mb` 设成 **20 MiB**：

- **代价**：更多的 `cudaMalloc` 调用（更慢的分配）；
- **收益**：**大幅减少显存碎片**。

**只在这一个阶段生效**，加载完就恢复成 `SIZE_MAX`。

> 💡 **性能视角**：这是个很聪明的取舍 —— 权重加载期间的分配模式是"很多大小不一的大块"，最容易产生碎片；而运行期的分配是"固定大小的 KV block"，碎片风险低。
> **在正确的阶段用正确的 allocator 配置。**

## 11.3 `determine_available_memory`：为什么必须真的跑一次

`vllm/v1/worker/gpu_worker.py:510`。

### 两条路径

```python
def determine_available_memory(self) -> int:
    if self.cache_config.kv_cache_memory_bytes is not None:
        # 路径 A：用户直接给了字节数 → 跳过 profiling
        # 但仍然要跑 model_runner.profile_run()，让模型按 max_num_batched_tokens 编译好
        ...
    else:
        # 路径 B：真跑一次假前向测峰值
        with memory_profiling(init_snapshot, weights_memory=model_runner.model_memory_usage) as result:
            model_runner.profile_run()
        if cudagraph_mode != NONE and cuda_alike:
            cudagraph_estimate = model_runner.profile_cudagraph_memory()
        available_kv_cache_memory_bytes = (
            requested_memory - profile_result.non_kv_cache_memory - cudagraph_estimate)
```

### 为什么要实测

激活内存、Inductor 的 workspace、CUDA Graph 的私有池，**都很难静态估算**：

- 激活取决于 batch 组成和 seq 长度分布；
- 图捕获的内存取决于捕获了多少 size、每个 size 的 buffer；
- attention kernel 的 workspace 取决于后端实现。

**实测是最可靠的方式。**

`profile_run()` 用的是 `initialize_dummy_weights`（`weight_utils.py:1294`）填的**随机小值**，所以它不做真实计算（几秒内完成）。

### 一些有意思的细节

```python
# 区分 transient_peak_headroom（激活峰值）与 steady total_consumed
# 建议 --kv-cache-memory 时保留 150 MiB 冗余
# 断言 init_free_memory >= free_gpu_memory（捕捉同卡上的其他进程）
```

**那个断言很实用**：如果初始化后的空闲显存比一开始还多，说明**有别的进程在和你抢显存**（或者有进程退出了）。这是一个廉价的一致性检查。

`VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS` 控制是否估算 CUDA Graph 的显存（默认开）。

> 💡 **性能视角**：`kv_cache_memory_bytes` 跳过的只是 profiling（几秒），**不会跳过编译**。
> 它的主要价值是**确定性** —— 在多租户/共享 GPU 的环境里，实测 profiling 会受邻进程影响，直接指定字节数更可控。

## 11.4 `compile_or_warm_up_model`：启动期的重头戏

`vllm/v1/worker/gpu_worker.py:747`。顺序很重要：

```text
1. 构造 warmup_sizes：
   = compile_sizes - cudagraph_capture_sizes
   + 每个没有覆盖的 compile_range 的 end
   → 逐个 _dummy_run(size, skip_eplb=True, remove_lora=False)，从大到小

2. kernel_warmup(self)

3. 若未 enforce_eager：
   cuda_graph_memory_bytes = model_runner.capture_model()
   → 与之前估算的 cudagraph_estimate 对比并打日志  ★ 验证估算

4. PP 最后一个 rank 才做 sampler warmup：
   max_num_reqs = min(max_num_seqs, max_num_batched_tokens)
   _dummy_run(...) + _dummy_sampler_run(hidden_states=last_hidden_states)
   ★ 必须在 capture_model 之后 —— 目的是在 empty_cache 造成碎片之前
     把最大形状的 logits/logprob buffer 预分配好

5. set_random_seed 重置
6. trigger_inductor_lazy_init
7. activate_jit_monitor       ← ★ 捕捉"运行期意外 JIT"，那会导致延迟尖峰
8. freeze_gc_heap
9. enable_gpu_sync_check
10. set_torch_threads_for_runtime
```

### 三个值得展开的点

**① warmup 顺序从大到小**

因为 Inductor 的编译缓存和 CUDA Graph 的显存池都是"按最大形状分配后复用"。**先跑大的，小的可以复用**；反过来的话大尺寸还要重新分配。

**② Sampler warmup 必须在 `capture_model` 之后**

注释里说得很清楚：目的就是在 `empty_cache` 造成碎片**之前**把最大形状的 buffer 预分配好。顺序错了会导致后续分配失败或退化。

**③ `activate_jit_monitor`**

**运行期的 JIT 编译是延迟尖峰的头号嫌疑**。vLLM 主动监控"是否在运行期发生了 JIT"，如果发生了会告警。这解释了为什么 warmup 要覆盖所有可能的 size —— **未覆盖的 size 会在第一个真实请求上触发编译**。

### `get_compilation_match_table`

```python
def get_compilation_match_table(self) -> dict[str, int]: ...   # :975
```

用来观测"实际运行的 batch 大小"与"编译/捕获覆盖的尺寸"的匹配情况。

> 💡 **性能视角**：如果压测时发现有大量请求落在**未捕获的 size** 上，会走 eager 路径 —— 表现为"大部分请求很快，偶尔几个特别慢"。
> 解决方式：调整 `cudagraph_capture_sizes` 覆盖你的实际 batch 分布。

## 11.5 CUDA Graph 与编译的启动时间控制

| 配置 | 效果 |
| --- | --- |
| `-O0` | 不编译不捕获 → **秒级启动** |
| `-O1` | PIECEWISE + 基础融合 → 十几秒 |
| `-O2`（默认） | FULL_AND_PIECEWISE + 全部融合 → 最长 |
| `--compilation-config '{"cudagraph_capture_sizes": [...]}'` | 减少捕获尺寸 → 直接减少捕获时间 |
| `--compilation-config '{"compile_sizes": [...]}'` | 减少编译尺寸 |
| `--enforce-eager` | 完全关闭 |
| AOT artifact + 缓存 | **把编译时间挪到构建阶段** |

### AOT 编译与环境变量

| 变量 | 作用 |
| --- | --- |
| `VLLM_USE_AOT_COMPILE` | 启用 AOT |
| `VLLM_USE_STANDALONE_COMPILE`（默认 `1`） | 用 standalone compile 路径 |
| `VLLM_FORCE_AOT_LOAD` | 强制加载 AOT artifact |
| `VLLM_USE_MEGA_AOT_ARTIFACT` | 用一个大的 artifact 文件 |
| `VLLM_CACHE_ROOT` | 编译缓存目录（默认 `~/.cache/vllm`） |
| `VLLM_COMPILE_DEPYF` | 用 depyf 生成可读代码（调试） |
| `VLLM_DEBUG_DUMP_PATH` | dump 编译产物 |

**生产实践**：在构建镜像时用**相同的配置**跑一次 warmup，把 `VLLM_CACHE_ROOT` 的内容打进镜像层。这样容器启动时编译缓存直接命中。

> ⚠️ **易错点**：编译缓存的 key 包含 vLLM 版本 + torch 版本 + 配置 hash。**改了任何一个配置，缓存就失效**。所以"预热镜像"时的配置必须和运行时完全一致。

## 11.7 显存管理：memory pool / workspace / sleep mode

### CuMem allocator 与 memory pool 标签

```python
with self._maybe_get_memory_pool_context(tag="weights"): ...   # 权重池
with self._maybe_get_memory_pool_context(tag="kv_cache"): ...  # KV 池
```

**分开的池让权重和 KV 能被独立回收/换出。** 这是 sleep mode 的基础设施。

相关配置：`ModelConfig.enable_cumem_allocator`。

### workspace

`vllm/v1/worker/workspace.py`（314 行）+ `_num_workspace_lanes`（`gpu_worker.py:101`）。

**Workspace 是"预分配的临时张量池"**，供 ModelRunner 内部使用（避免每步分配临时显存）。
`init_workspace_manager` 在 `init_device` 里被调用。

### sleep mode

`Worker.sleep(level)`（`gpu_worker.py:234`）/ `wake_up(tags)`（`:269`）。

| level | 行为 |
| --- | --- |
| 1 | **offload 权重到 CPU**（显存释放，但保留内容） |
| 2 | **丢弃权重**（需要重新加载） |

**level 2 的一个关键细节**（`:234` 附近）：

```python
if level == 2:
    # 先把所有模型 buffer 克隆到 CPU
    for name, buf in model.named_buffers():
        self._sleep_saved_buffers[name] = buf.clone()
```

**为什么？** 因为 `suspend` 会释放 allocator 管理的显存，而**buffer 是非持久状态**（例如 RoPE 的频率缓存），suspend/resume 之后就没了。必须单独保存和恢复。

`sleep` 还会**轮询等待显存真正释放**（ROCm 上最多 5 秒）—— 因为显存释放是异步的。

`wake_up(tags)` 的 `tags` 支持**只唤醒 KV cache 而不唤醒权重** —— RL rollout 场景需要这个（只重置 KV，权重不变）。

相关配置：`ModelConfig.enable_sleep_mode`、`sleep_mode_backend`。

### 权重 offload

`vllm/config/offload.py`：`cpu_offload_gb`、`offload_group_size`、`offload_num_in_group`、`offload_prefetch_step`、`offload_params`。

**这是"把暂时不用的权重放到 CPU、需要时预取回来"**，与 sleep mode 的区别是它**在推理过程中动态换入换出**。

> ⚠️ **性能视角**：权重 offload 的收益高度依赖访问模式。如果每层每步都要用（正常情况），offload 只会让性能崩溃。它主要服务于"多个模型共享一张卡、轮流使用"的场景。

## 11.8 权重热更新（RL 场景）

`Worker` 里有一组方法：

```python
_check_weight_transfer_engine()      # :1303
init_weight_transfer_engine(...)     # :1310
start_weight_update()                # :1324
update_weights(update_info)          # :1369
finish_weight_update()               # :1406
```

对应 `ParallelConfig` 侧无，而是 `ModelConfig` 的 `weight_transfer` 相关配置 + `vllm/config/weight_transfer.py`。

**RL 训练场景需要在推理引擎里原地更新权重**（训练完一批就同步给推理）。这比"重启引擎"快几个数量级。

`ModelConfig.weight_version` / `set_weight_version` 用于版本管理（配合 `CUDAGraphWrapper.clear_all_graphs` 在权重更新后清空图 —— 因为图里可能 bake 了旧的权重地址）。

## 11.9 启动时间优化清单

| 手段 | 收益 | 代价 |
| --- | --- | --- |
| `safetensors_prefetch_num_threads` | 多 rank 冷启动从分钟到几十秒 | 需要足够内存放 checkpoint |
| `--load-format fastsafetensors`（或 runai） | 更快的 I/O 路径 | 需要装额外库 |
| `enable_ep_weight_filter` | MoE 模型加载量与显存峰值大降 | — |

| `initialization_dummy_weights` | profiling 用随机权重，几秒完成 | — |

## 11.10 本章小结

- 启动时间的大头是**编译 + 图捕获**，其次是权重加载；两者都有成熟的优化手段。
- 权重加载的六个手段：预取、更快的格式、并行、EP 过滤、加载期 allocator 调优、`target_device` 直建。
- `determine_available_memory` 必须实测（激活/图池无法静态估算），除非显式给 `kv_cache_memory_bytes`。
- `compile_or_warm_up_model` 的顺序有硬约束（大到小、sampler 在 capture 后）。
- `activate_jit_monitor` 主动捕捉运行期 JIT —— 那是延迟尖峰的元凶。
- 注册表懒加载 + 磁盘缓存能力位，避免 import 几百个模块。
- sleep mode 的 level 2 必须手动保存非持久 buffer。
- 权重热更新是 RL 场景的必需能力，权重更新后要清空 CUDA Graph。

⚠️ **易错点**
- 预热镜像时用的配置必须与运行时**完全一致**，否则编译缓存不命中。
- `--enforce-eager` 会跳过整个编译/捕获阶段，启动快但性能差 —— 别用它来做容量规划。
- `cpu_offload_gb` 不是"省显存神器"，在常规推理下会让性能崩溃。
