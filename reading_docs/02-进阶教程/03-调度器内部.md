## 3.2 预算的三个来源

```python
token_budget = self.max_num_scheduled_tokens                       # 本步总 token
input_budget = self.scheduler_config.max_num_batched_tokens        # 输入 token
draft_slots  = spec.max_num_new_slots_for_drafting if spec else 0  # 投机预留
```

每调度一个请求：

```python
token_budget -= num_new_tokens
input_budget -= num_new_tokens + draft_slots
```

**为什么要有两个预算？** `input_budget` 是**模型输入的 token 上限**（与 `max_num_batched_tokens` 对应），而 `token_budget` 在异步调度下可能被设成**额外的上限**（`max_num_scheduled_tokens`），用于给"调度超前"留出空间。
在普通（非异步）调度下两者接近，但语义不同。

`draft_slots` 的存在是因为投机解码的草案 token 也要占模型输入的槽位 —— 如果不预留，草案 token 会把正常 token 挤掉。

## 3.3 为什么 `continue` 而不是 `break`

```python
if num_new_tokens == 0:
    # The request cannot be scheduled because one of the following reasons:
    # 1. No new tokens to schedule. This may happen when
    #    (1) PP>1 and we have already scheduled all prompt tokens but they are
    #        not finished yet.
    #    (2) Async scheduling and the request has reached to either its
    #        max_total_tokens or max_model_len.
    # 2. The encoder budget is exhausted.
    # 3. The encoder cache is exhausted.
    # 4. Insufficient budget for a block-aligned chunk in hybrid models with
    #    mamba cache mode "align".
    # 5. Insufficient budget to keep a multi-module MTP prefill chunk out of
    #    the prefill-lookahead window.
    # NOTE(woosuk): Here, by doing `continue` instead of `break`,
    # we do not strictly follow the FCFS scheduling policy and
    # allow the lower-priority requests to be scheduled.
    req_index += 1
    continue
```

**这是一个重要的设计取舍**：严格 FCFS 会"队首阻塞"（head-of-line blocking）—— 第一个请求因为预算原因排不上，后面所有请求都陪着等。
vLLM 选择**打破严格 FCFS**，让后面的请求先跑。

> 💡 **性能视角**：这个取舍提升了吞吐（GPU 不被浪费），代价是**公平性**（晚到的请求可能先完成）。
> 对延迟敏感的业务要意识到这一点：**FCFS 不等于"按到达顺序完成"**。

## 3.4 抢占的完整语义

### 触发条件

`allocate_slots` 返回 `None`（`scheduler.py:664`）。`None` 的含义在 `KVCacheManager.allocate_slots` 里：**空闲 block 数不够**（还要扣掉 `reserved_blocks` 和 `watermark`）。

### victim 选择

```python
if self.policy == SchedulingPolicy.PRIORITY:
    preempted_req = max(self.running, key=lambda r: (r.priority, r.arrival_time))
    victim_index = self.running.index(preempted_req)
    del self.running[victim_index]
    if victim_index < req_index:
        req_index -= 1              # ★ 维护循环游标
else:
    preempted_req = self.running.pop()      # FCFS：队尾
```

FCFS 下 `pop()` 就是"踢掉最后一个进来的"。这个语义有点反直觉（通常抢占应该踢"最重要的"），但 vLLM 的逻辑是：**刚进来的请求还没积累多少 KV，踢它损失最小**。

### 已经调度过的 victim 要被回滚

```python
if preempted_req in scheduled_running_reqs:
    scheduled_running_reqs.remove(preempted_req)
    restored = num_scheduled_tokens.pop(preempted_req_id)
    token_budget += restored                  # 预算还回去
    input_budget += restored + draft_slots
    req_to_new_blocks.pop(preempted_req_id)
    scheduled_spec_decode_tokens.pop(preempted_req_id, None)
    # 编码器预算也要还
```

**这段代码很重要**：抢占可以发生在同一个 step 内（先被调度，后来因为别的请求需要空间而被踢）。此时必须**完整回滚所有已记录的副作用**，否则预算和 KV 账目会对不上。

### `_preempt_request` 的完整后果

`vllm/v1/core/sched/scheduler.py:1405`：

```python
self._free_request_blocks(request)         # ① 释放全部 KV block
self.encoder_cache_manager.free(request)   # ② 释放编码器缓存
self._inflight_prefills.discard(request)
request.status = RequestStatus.PREEMPTED
request.num_computed_tokens = 0            # ③ ★ 进度归零 → 重算
if request.spec_token_ids:
    request.spec_token_ids = []
request.drop_stale_output = ...
request.num_stale_output_tokens = request.num_in_flight_tokens
request.num_output_placeholders = 0
request.num_preemptions += 1               # ④ 计数（可观测）
self.waiting.prepend_request(request)      # ⑤ 插到等待队首（不是队尾！）
self.reset_preempted_req_ids.add(request.request_id)
```

**三个关键点**：

1. **`num_computed_tokens = 0`** —— 整段进度清零，意味着重算。**但如果开了 prefix caching，重算时 `get_computed_blocks` 能命中大部分**，实际代价远小于"从头算"。这就是 prefix caching 在高并发下的第二重价值。
2. **`prepend_request`** —— 被抢占的请求下一次调度时**优先于**新来的请求。这是防止"抢占风暴"的关键：如果插到队尾，它可能反复被抢占，永不完成（livelock）。
3. **`num_preemptions` 计数** —— 最终体现在 `SchedulerStats.preempted_requests`。**这个数字持续 > 0 是最明确的"显存配置不足"信号。**

### `drop_stale_output`：异步调度下的正确性细节

代码注释说得很清楚：

```python
# Async scheduling: mark all in-flight output as stale. Its tokens are
# still delivered on return (dropping them would perturb spec-decode
# acceptance) but must not mutate the reset counters; each step drains
# its share in update_from_output.
```

异步调度下，被抢占时可能还有"在途"的采样结果（已提交给 GPU、还没返回）。这些结果不能简单丢弃（会打乱投机解码的接受计数），但也不能用来推进状态（因为 `num_computed_tokens` 已经归零了）。所以标记为 **stale**：**照常投递给用户，但不更新内部计数**。

> 💡 **性能视角**：这是异步调度复杂度的一个缩影 —— 它把"状态一致性"的推理从一步内扩展到"流水线深度"范围内。收益是 CPU 不空转，代价是这类边界情况的处理代码。

## 3.5 WAITING 队列的调度细节

### 三个队列

```python
self.waiting: RequestQueue
self.skipped_waiting: RequestQueue
self.reset_preempted_req_ids: set[str]
```

`_select_waiting_queue_for_scheduling`（`scheduler.py:2240`）决定这轮从哪个队列取：

```python
def _select_waiting_queue_for_scheduling(self) -> RequestQueue | None:
    if len(self.waiting) > 0:
        return self.waiting
    elif len(self.skipped_waiting) > 0:
        return self.skipped_waiting
    return None
```

**`waiting` 优先于 `skipped_waiting`**。`skipped_waiting` 是"这一步尝试过但因为预算/LoRA/blocked 状态被跳过的"。这么做是为了保证新请求有机会被看到（否则饥饿）。

但注意循环里 `step_skipped_waiting` 的用法：

```python
# re-queue requests skipped in this pass ahead of older skipped items.
if step_skipped_waiting:
    self.skipped_waiting.prepend_requests(step_skipped_waiting)
```

本轮被跳过的放到 `skipped_waiting` 的**前面**（`prepend_requests`）。这样在 `skipped_waiting` 内部是"按最后尝试时间排序"（最近尝试的排前面），避免同一个请求反复被排到后面。

### `blocked` 状态的提升

```python
if (self._is_blocked_waiting_status(request.status)
        and not self._try_promote_blocked_waiting_request(request)):
    request_queue.pop_request()
    step_skipped_waiting.prepend_request(request)
    continue
```

`_is_blocked_waiting_status`（`:2227`）覆盖 `WAITING_FOR_REMOTE_KVS`、`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR` 等。
`_try_promote_blocked_waiting_request`（`:2859`）检查外部条件是否满足（例如远端 KV 传输已完成），满足就提升为 `WAITING`。

**这个设计避免了两个坏结果**：(a) 阻塞请求占着队首不放；(b) 每步都为一个还没就绪的请求做完整重试。

### `pad_spec_decode`：为了 CUDA Graph 形状而拒绝调度

```python
# Pad new decode requests to uniform spec decoding size to
# preserve full cudagraph for this step.
if ((self.num_spec_tokens > 0 and self.dynamic_sd_lookup is None)
        and self.num_sampled_tokens_per_step > 0
        and num_new_tokens == 1
        and (scheduled_running_reqs and not prefill_scheduled)):
    padded_num_tokens = 1 + self.num_spec_tokens
    if (num_computed_tokens + padded_num_tokens + self.num_sampled_tokens_per_step
            <= self.max_model_len):
        if padded_num_tokens > request_token_budget:
            break                      # ★ 宁可不调度
        num_new_tokens = padded_num_tokens
        pad_spec_decode = True
```

逐条解释这个条件链：

| 条件 | 含义 |
| --- | --- |
| `num_spec_tokens > 0` | 开了投机解码 |
| `dynamic_sd_lookup is None` | 不是动态投机长度 |
| `num_new_tokens == 1` | 这是一个纯 decode 请求 |
| `scheduled_running_reqs` 且 `not prefill_scheduled` | 本步没有 prefill，是纯 decode 批次 |
| `padded_num_tokens <= request_token_budget` | 有预算容纳 padding |

满足时，把这个请求的 `num_new_tokens` 从 1 **扩成 `1 + K`**（K = 投机 token 数）。这样整个 batch 的形状是 **uniform** 的，可以走 full CUDA Graph。
如果预算不够，宁可 `break`（**这个请求这步不跑**）也不破坏 uniform 形状。

> 💡 **性能视角（极佳案例）**：这是"**形状一致性 > 单步吞吐**"的直接体现。
> full CUDA Graph 的收益（消除 launch 开销）被认为大于"多调度一个请求"的收益。
> 这也解释了为什么 `--max-num-batched-tokens` 在开启投机解码时需要留出余量。

### `enable_chunked_prefill=False` 的后果

```python
if (not self.scheduler_config.enable_chunked_prefill
        and num_new_tokens > request_token_budget):
    break         # 整个 waiting 循环退出
```

关掉 chunked prefill 后，一个超长 prompt 请求会让整个 scheduling 循环 `break` —— **decode 请求也只能等下一步**。这是长 prompt 场景下延迟尖峰的根源。

## 3.6 `update_from_output`：采样结果的翻译

`vllm/v1/core/sched/scheduler.py:1802`。开头几行就说明了它的输入：

```python
sampled_token_ids = model_runner_output.sampled_token_ids
logprobs = ...
num_scheduled_tokens = scheduler_output.num_scheduled_tokens
pooler_outputs = ...
num_nans_in_logits = ...
kv_connector_output = ...
cudagraph_stats = ...
```

主要工作：

### ① 延迟释放的 block 在这里才真正归还

```python
# Every GPU write enqueued by this and earlier steps has completed, so it is
# safe to return deferred-free blocks to the pool.
if self.defer_block_free and scheduler_output.total_num_scheduled_tokens > 0:
    self.processed_step_seq += 1
    self._drain_deferred_frees()
```

**为什么 block 释放要延迟？** 因为异步调度下，调度器可能在 GPU 还在用某个 block 的时候就想释放它（因为下一步的状态已经决定了）。
`defer_block_free` 机制把释放推迟到"确认这一步的 GPU 写已经完成"之后。相关方法：`_free_cow_retained_blocks`（`:2537`）、`_drain_deferred_frees`（`:2548`）。

### ② 投机解码：修正 `num_computed_tokens`

```python
num_accepted = max(len(generated_token_ids) - num_sampled, 0)
num_rejected = num_draft_tokens - num_accepted
if num_rejected > 0:
    request.num_computed_tokens -= num_rejected       # ★ 把被拒的草案位置退回去
```

**这是调度器与投机解码的接口**：草案被拒绝的部分，其 KV 是"算过但无效"的，必须从 `num_computed_tokens` 里扣掉，下步会重新算（覆盖写）。

### ③ 统计汇总

```python
spec_decoding_stats.observe_draft(num_draft_tokens=..., num_accepted_tokens=...)
```

`SpecDecodingStats.num_accepted_tokens_per_pos` 的曲线是调 `num_speculative_tokens` 的依据（见入门教程第 9 章）。

### ④ 结束判定与 `finished_req_ids`

`_free_request`（`:2480`）→ `_free_request_blocks`（`:2522`）→ 把 req_id 加进 `self.finished_req_ids`。
这个集合随后被放进下一个 `SchedulerOutput`，**通知 worker 释放对应的 `CachedRequestState`**。这是"上行通知"的唯一通道。

## 3.7 异步调度（async scheduling）

配置：`SchedulerConfig.async_scheduling`。这是当前版本最重要的性能特性之一。

### 它解决的问题

普通流程是串行的：

```text
step t:   调度 → 执行 → 采样 → 更新状态 → 调度 step t+1
                                      ↑
                            必须等 GPU 采样结果回来
```

采样结果需要 D2H 拷贝（几微秒到几十微秒）加 Python 处理，这段时间 GPU 是**空闲的**。

异步调度让调度器**不等采样结果就推进下一步**：

```text
step t:   调度 → 执行 → 提交
step t+1:      调度（用"乐观假设"）→ 执行 → 提交
```

### 关键机制：输出占位符（`num_output_placeholders`）

调度器需要一个"还没确定但假定会生成"的 token 位置。相关字段（`vllm/v1/request.py`）：

| 字段 | 含义 |
| --- | --- |
| `num_output_placeholders` | 已假定但未确认的输出 token 数 |
| `num_in_flight_tokens` | 已提交给 GPU 但结果未回 |
| `num_stale_output_tokens` | 结果已作废（被抢占等）但在途 |
| `drop_stale_output` | 是否丢弃 stale 输出 |

调度时：

```python
num_new_tokens = (request.num_tokens_with_spec
                  + request.num_output_placeholders      # ★ 乐观地用占位符
                  - request.num_computed_tokens)
```

采样结果回来后，`update_from_output` 把占位符换成真实 token 并修正计数。

### 与 worker 侧的配合

Worker 侧要能在"没有 CPU 端 token id"的情况下构造下一步的输入：

- `_prepare_input_ids`（`gpu_model_runner.py:1794`）的异步路径**在 GPU 上 scatter** 上一步的采样结果（`prev_sampled_token_ids` + `prev_positions` 映射），不做 D2H。
- `AsyncGPUModelRunnerOutput`（`gpu_model_runner.py:293`）把输出包装成"稍后可在独立 stream 上解析"的形式。
- `input_batch.set_async_sampled_token_ids`（`gpu_input_batch.py:1028`）保存结果供下一步使用。

### 代价清单

| 代价 | 说明 |
| --- | --- |
| 输出延迟增加 | 结果要等流水线排空 |
| `max_model_len` 需预留 | 超前调度会多算 token |
| 复杂度 | 占位符/stale/在途计数的一致性推理 |
| 破坏 CUDA Graph uniform 形状的风险 | 代码里有专门的逻辑避免"部分草案"导致形状不齐 |

## 3.8 自定义调度器

`SchedulerConfig.scheduler_cls`（`vllm/config/scheduler.py:92`）允许替换调度器实现。
接口在 `vllm/v1/core/sched/interface.py`（`SchedulerInterface`，262 行），定义了必须实现的方法集合。

**这是扩展 vLLM 最干净的入口之一**：如果你的业务有特殊的公平性/优先级/SLO 需求，实现 `SchedulerInterface` 比改 `scheduler.py` 安全得多。

## 3.9 三个可以直接观测的指标

| 指标 | 位置 | 意味着 |
| --- | --- | --- |
| `num_waiting_reqs` | `SchedulerStats` | > 0 → 请求在排队（可能是显存、可能是 `max_num_seqs`） |
| `num_skipped_waiting_reqs` | `SchedulerStats` | > 0 → 有请求这步被跳过（预算/LoRA/blocked） |
| `preempted_requests` | `PrefixCacheStats` | > 0 → **重复计算**，最贵的浪费 |

## 3.10 本章小结

- `schedule()` 两轮循环 + 两个预算；allocate 失败即抢占。
- `continue` 而非 `break` 打破严格 FCFS，换取吞吐。
- 抢占 = 释放全部 block + `num_computed_tokens = 0` + 插队首 + 计数。prefix caching 是它的止痛药。
- 同 step 内抢占要回滚所有已记录的副作用（预算/block/encoder）。
- `pad_spec_decode` 是"形状一致性优先于吞吐"的教科书案例。
- `update_from_output` 修正投机解码的 `num_computed_tokens`，并延迟释放 block。
- 异步调度用占位符超前推进，代价是延迟、`max_model_len` 余量和复杂度。
- `scheduler_cls` 是扩展入口。

⚠️ **易错点**
- `num_computed_tokens` 会在一个 step 内被推进两次（`_update_after_schedule` 和 `update_from_output`），读代码时要分清上下文。
- `token_budget` 在抢占回滚时会被"加回来"，所以不能用"初始值 - 消耗"来简单推断。
