## 9.1 all-reduce 的七条路径

`vllm/distributed/device_communicators/cuda_communicator.py:278` `all_reduce` 的**分派顺序**（这就是实际的优先级）：

```python
def all_reduce(self, input_):
    # ① NCCL symmetric memory（symm mem allreduce）
    if (pynccl_comm is not None and not use_fi_ar
            and should_nccl_symm_mem_allreduce(pynccl_comm.world_size, input_)):
        out = torch.ops.vllm.all_reduce_symmetric_with_copy(input_)
        if out is not None:
            return out
    # ② Quick AllReduce
    if qr_comm is not None and not qr_comm.disabled and qr_comm.should_quick_allreduce(input_):
        return qr_comm.quick_all_reduce(input_)
    # ③ FlashInfer AllReduce
    if use_fi_ar:
        return fi_ar_comm.all_reduce(input_)
    # ④ AITER custom all-reduce（ROCm）
    if aiter_ar_comm is not None and ... and aiter_ar_comm.should_custom_ar(input_):
        return aiter_ar_comm.custom_all_reduce(input_)
    # ⑤ Custom AllReduce
    if ca_comm is not None and ... and ca_comm.should_custom_ar(input_):
        return ca_comm.custom_all_reduce(input_)
    # ⑥ torch symmetric memory
    if symm_mem_comm is not None and symm_mem_comm.should_use_symm_mem(input_):
        return symm_mem_comm.all_reduce(input_)
    # ⑦ PyNccl（兜底）
    ...
```

**每个分支都有一个 `should_*` 判据**，通常检查：

- 张量大小是否在有效区间（太小 → launch 开销主导；太大 → 分块策略不同）；
- dtype 是否支持；
- 是否有 P2P 能力；
- world size 是否匹配。

### 为什么自研 all-reduce 能比 NCCL 快

| 维度 | NCCL | Custom AllReduce |
| --- | --- | --- |
| 通用性 | 任意拓扑、任意大小 | 只支持单机、TP ≤ 8、有 P2P |
| 算法 | Ring / Tree，分多步 | **one-shot / two-shot** |
| Launch 次数 | 多次（每个 chunk 一次） | **一次 kernel** |
| 启动开销 | 需要通信库状态机 | 直接用 P2P 写对端显存 |

**核心差异在"一次 kernel"**。TP 的 all-reduce 每层两次，层数几十 —— 每层省几次 launch 就是几百次。

`custom_all_reduce.py` 在 SM90+ 还能用 **multimem**（多播显存）进一步加速。

### 什么情况下自研实现反而更慢

| 场景 | 原因 |
| --- | --- |
| 跨节点 | P2P 不适用（NVLink 域外） |
| TP 很大（>8） | one-shot 的显存开销 = `(world_size-1) × tensor_size` |
| 张量很小 | launch 开销占比高，但这些实现有 size 下限判断（`should_custom_ar`） |
| 张量非常大 | 分块策略不如 NCCL 的 ring 高效 |
| 有其他进程干扰 | P2P 握手失败会回退 |

**排查方式**：`_log_all_reduce_backend_selection`（`cuda_communicator.py:~222-276`）会把实际启用的后端按分派顺序打日志。启动时看一眼就知道走的是哪条路。

> 💡 **性能视角**：`--disable-custom-all-reduce` **通常会让性能变差**。如果你"为了稳定"关掉它，等于放弃了 TP 场景最重要的延迟优化。只有在握手失败、或复现某些精度问题时才该关。

## 9.2 一条重要的限制：只有 TP 组能用自研实现

```python
# cuda_communicator.py:50
if "tp" not in unique_name:
    # custom allreduce or torch symm mem can be used only by tp
    use_custom_allreduce = False
    use_torch_symm_mem = False
    use_flashinfer_allreduce = False
    use_aiter_allreduce = False
```

**为什么？** 因为这些实现都假设"所有 rank 参与、平铺在 NVLink 全互联域内"。

- DP 组：不同 rank 在不同引擎里，不是每步都通信；
- PP 组：通信模式是 P2P（send/recv），不是 all-reduce；
- EP 组：通信模式是 all-to-all。

所以这些组只能用 `pynccl` 或 `torch.distributed` 的通用实现。

## 9.3 `batch_invariant` 与通信的冲突

```python
use_flashinfer_allreduce = (
    envs.VLLM_ALLREDUCE_USE_FLASHINFER and not envs.VLLM_BATCH_INVARIANT
)
```

注释解释了原因：

```python
# FlashInfer all-reduce does not provide a fixed reduction order.
```

**浮点加法不满足结合律** —— `(a+b)+c ≠ a+(b+c)`。如果不同 batch 组成导致归约顺序变化，同样的输入可能产出**不同的 bit pattern**，进而导致不同的采样结果。

`VLLM_BATCH_INVARIANT=1` 要求"同样的 prompt 在不同的 batch 组成下产出完全相同的输出"。此时必须：

- 禁用 FlashInfer all-reduce（归约顺序不固定）；
- 禁用 symm mem all-reduce（同理）；
- 用 PyNccl（提供固定的归约顺序）。

**代价是性能**。这是"可复现性 vs 吞吐"的又一次显式权衡。

## 9.4 `graph_capture`：让通信进图

`parallel_state.py:659`：

```python
@contextmanager
def graph_capture(self, graph_capture_context=None):
    # 取 custom all-reduce 的 capture context
    # ROCm 下取 aiter AR 的 capture context
    ...
    stream.wait_stream(curr_stream)
    with torch.cuda.stream(stream), maybe_ca_context, maybe_aiter_context:
        yield
```

**为什么必须有这个机制？**

1. **通信 buffer 必须在同一 stream 上分配和使用**。如果 capture 用一个 stream、replay 用另一个，会读到错误地址。
2. **custom all-reduce 需要"预热"**（第一次调用时会分配/初始化 P2P buffer），必须在 capture 之前完成。
3. **不能有动态分配**（图捕获期间 `cudaMalloc` 会失败或被禁止）。

相关的调用点：`Worker.compile_or_warm_up_model` 期间会进入 `graph_capture` 上下文做 warmup。

## 9.5 MoE 的 all-to-all

### 通信模式

```text
1. gate 算出每个 token 要发给哪些专家
2. dispatch（all-to-all）：把 token 发到持有目标专家的 rank
3. 本地专家计算
4. combine（all-to-all）：把结果发回来
```

`parallel_state.py` 里对应三个方法：

```python
dispatch_router_logits(...)   # :1374
dispatch(...)                 # :1394
combine(...)                  # :1416
```

### 实现清单

`vllm/distributed/device_communicators/all2all.py` + `vllm/model_executor/layers/fused_moe/prepare_finalize/`：

| 实现 | 对应文件 | 特点 |
| --- | --- | --- |
| 无 EP | `no_dp_ep.py` | 恒等（不通信） |
| 朴素 DP+EP | `naive_dp_ep.py` | 参考实现 |
| DeepEP 高吞吐 | `deepep_ht.py` | 大 batch 优化 |
| DeepEP 低延迟 | `deepep_ll.py` | 小 batch（decode）优化 |
| DeepEP v2 | `deepep_v2.py` | 新版 |
| FlashInfer NVLink 单边/双边 | `flashinfer_nvlink_one_sided.py` / `_two_sided.py` | NVLink 域内 |
| NIXL EP | `nixl_ep.py` | 跨节点 RDMA |
| Mori | `mori.py` | — |
| Batched | `batched.py` | — |

选择：`--all2all-backend`（`ParallelConfig.all2all_backend`）。

> 💡 **性能视角**：**MoE 的 all-to-all 是延迟敏感的**。
> 每层两次 all-to-all，层数几十 —— 即使每次只有几十微秒，累积起来也很可观。
> 而且它的通信量取决于**路由的分散程度**：如果 token 均匀分给所有专家，通信量大；如果有热点专家，通信量小但负载不均。
> 这就是 **EPLB（Expert Parallel Load Balancer）** 存在的原因。

### EPLB

`ParallelConfig.enable_eplb` + `eplb_config`。相关代码：`GPUModelRunner.eplb_step`（`gpu_model_runner.py:3466`）、`setup_eplb_from_mapping`（`:3481`）。

它**在线统计专家负载并重新放置专家**。代价是统计开销和专家权重的迁移。

`expert_placement_strategy`（`"linear"` 等）决定初始放置方式。

`enable_ep_weight_filter`（`:56`）是一个容易被忽略的启动优化：**EP 下只加载本 rank 需要的专家权重**，显著减少加载时间和显存峰值。

## 9.6 ubatching（DBO）：CPU-GPU 两级流水

`ParallelConfig.enable_dbo` + `ubatch_size`。实现：`vllm/v1/worker/ubatching.py`、`ubatch_utils.py`、`gpu_ubatch_wrapper.py`（537 行）。

### 核心思想

把一个 batch 切成两个 micro-batch（ubatch），让 **ubatch A 的 GPU 执行**与 **ubatch B 的 CPU 准备**重叠：

```text
时间 →
CPU:  [准备 A][准备 B      ][准备 A'     ]
GPU:           [执行 A     ][执行 B      ][执行 A']
               ↑ 重叠区间
```

### 触发阈值

```python
dbo_decode_token_threshold: int = 32      # decode 超过这么多 token 才启用
dbo_prefill_token_threshold: int = 512    # prefill 超过这么多 token 才启用
```

**为什么要阈值？** 因为切分本身有开销（两次 forward、通信要分裂成两次）。**batch 太小时，重叠的收益抵不过切分的开销。**

### 与调度器/ModelRunner 的配合

- 调度器：`use_ubatching` 时**禁用 cascade attention**（`gpu_model_runner.py:4336`）—— 因为 cascade 的公共前缀假设与 ubatch 的切分冲突。
- `_get_slot_mappings` 会**按 ubatch 切片**返回列表（每个 ubatch 一份）。
- `_allow_microbatching`（`gpu_model_runner.py:3970`）判断当前 batch 是否适合切分。

### `gpu_ubatch_wrapper.py`

它把 `execute_model` 包成一个可用 CUDA Stream 交错的形式。关键挑战是**共享状态**（`InputBatch`、block table）在两个 ubatch 之间的一致性 —— 两个 ubatch 的操作必须不冲突。

⚠️ **实践建议**：DBO 是进阶特性，收益高度依赖负载和硬件。**先确认基础优化（CUDA Graph、编译、量化）都到位了，再考虑它。**

## 9.7 PP 的 bubble 与异步重叠

### Bubble

PP 把层切到不同 stage。朴素串行下，stage 0 算完 stage 1 才能开始 → 大量空闲。

### vLLM 的处理

1. **异步调度 + micro-batch**：让多个 batch 流水起来。
2. **`AsyncIntermediateTensors`**（`gpu_worker.py:143`）：PP 传 activation 时返回一个"惰性张量"，**真正访问数据时才等通信**：

```python
class AsyncIntermediateTensors(IntermediateTensors):
    def wait_for_comm(self) -> None: ...      # :157
    def __getattribute__(self, name):          # :168
        # 访问张量属性前先等通信完成
```

这让"接收 activation"与"其他 CPU 工作"重叠。

3. **`isend_tensor_dict` / `irecv_tensor_dict`**（`parallel_state.py:1129` / `:1251`）：非阻塞版本。`_reap_completed_isends`（`:1092`）回收已完成的 isend，**防止源张量被无限持有**。

```python
# GroupCoordinator 自己持有 source tensor 在 _pending_isends 里，
# 下一次异步 isend 时惰性回收，所以调用方不需要等
```

4. **调度器里的 PP 门控**：

```python
if self.current_step < request.next_decode_eligible_step:
    # V2+PP+async: enforce `pp_size` steps between same-req decodes
    # to match worker-side sampled-tokens broadcast slot ring cadence.
    req_index += 1
    continue
```

**同一个请求的两次 decode 之间必须间隔 `pp_size` 步**，因为 worker 侧的采样 token 广播环有 `pp_size` 个槽位。

5. **`_pp_broadcast_prev_sampled_token_ids`**（`gpu_model_runner.py:4911`）/ `_pp_receive_prev_sampled_token_ids_to_input_batch`（`:4928`）：让第一个 PP stage 直接拿到最后一个 stage 的采样结果，**绕过调度器**。

> ⚠️ **易错点**：PP 与异步调度、CUDA Graph、投机解码的交互非常复杂。**入门阶段不要碰 PP**，它带来的复杂度远超收益（除非模型确实跨机）。

## 9.8 `broadcast_tensor_dict` 的自动优化

`parallel_state.py:952` + `_should_use_all_gather`（`:1034`）：

```python
def _should_use_all_gather(self, key, numel, all_gather_group, all_gather_tensors) -> bool:
    if all_gather_group is None:
        return False
    use_all_gather = numel % all_gather_group.world_size == 0
    if all_gather_tensors is not None:
        use_all_gather = all_gather_tensors.get(key, use_all_gather)
    return use_all_gather
```

PP 传 activation 的默认方式是 `broadcast`（rank 0 发，其他人收）。但如果**张量元素数能被 world_size 整除**，可以改用 `all_gather`：

- broadcast：1 个 rank 写 N-1 个 rank 读 → 发送方带宽是瓶颈；
- all_gather：每个 rank 贡献 1/N，同时接收 → 带宽被充分利用。

**这是一个"按张量形状自动选通信原语"的优化**，用户不用配置。

`all_gatherv` / `reduce_scatterv`（`:752` / `:778`）是变长版本，配合 split group 使用。

## 9.9 DP 的同步机制

### `shm_broadcast.MessageQueue`

DP 之间需要同步的东西很少（"这一步要不要跑"、采样结果的广播、负载统计），所以**不用 NCCL，用共享内存**。

好处：
- 不需要通信库的启动开销；
- 延迟比 NCCL 低（对小消息）；
- 不占用 GPU 资源。

`ParallelConfig.disable_nccl_for_dp_synchronization` 控制是否完全禁用 NCCL 做 DP 同步。

### sentinel 机制

`vllm/v1/worker/sentinel/`：用于检测 DP rank 的存活和同步状态。

### 同步前向（MoE 必需）

MoE 模型在 DP 下，**所有 rank 必须同时进入前向**，否则 expert 的 all-to-all 会挂死。`DPCoordinatorProc` 用 "wave" 机制实现（`coordinator.py:460` `_send_start_wave`）。

`EngineCore._should_throttle_prefills`（`core.py:592`）与 `Scheduler.schedule(throttle_prefills=...)` 就是 DP 预填充均衡的接口：

```python
defer_prefills = (throttle_prefills and not self.prefill_capacity_bound) \
    and any(not r.is_prefill_chunk for r in self.running)
```

**思想**：如果某个 DP rank 的 prefill 太多，就把它的 prefill 推迟到"节奏对齐"的步，让各 rank 的步调一致。

## 9.11 本章小结

| 机制 | 收益 | 代价/限制 |
| --- | --- | --- |
| Custom AllReduce | 单次 kernel 完成归约 | 仅单机 TP≤8；跨机/大张量会回退 |
| Quick/FlashInfer/symm-mem AR | 不同 size 区间的更优解 | 归约顺序不固定（与 batch invariant 冲突） |
| `graph_capture` | 让通信进 CUDA Graph | 初始化复杂度 |
| 仅 TP 组用自研 AR | 正确性 | DP/PP/EP 只能用通用实现 |
| MoE all-to-all | 让专家分布到多卡 | 延迟敏感，受路由分散度影响 |
| EPLB | 消除专家热点 | 统计 + 迁移开销 |
| ubatching/DBO | CPU-GPU 两级重叠 | 切分开销，与 cascade attention 冲突 |
| PP 异步重叠 | 减少 bubble | 与异步调度/投机解码交互复杂 |
| `broadcast` → `all_gather` | 利用发送方带宽 | 需要 numel 整除 |
| `enable_ep_weight_filter` | 启动更快、显存峰值更低 | — |

⚠️ **易错点**
- `VLLM_BATCH_INVARIANT=1` 会禁用多种 all-reduce 实现，性能下降是预期行为。
- `--disable-custom-all-reduce` 不是"更稳定"的同义词，通常只是更慢。
- DBO 与 cascade attention 互斥；PP 与异步调度/投机解码有复杂的门控条件。
